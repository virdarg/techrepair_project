# План тестирования TechRepair

## 1. Цель и область
Проверить авторизацию и роли, добавление техники, запись/отмену услуг, ограничения БД, транзакционность, отчёты и аудит. Тестовая БД создаётся во временной папке для каждого теста; рабочая `techrepair_app.db` не изменяется.

## 2. Уровни
- **Модульное (unittest/xUnit):** проверки AuthService и валидации RepairService на валидных и невалидных входных данных.
- **Интеграционное:** BLL + DAL + SQLite в изолированной временной БД, включая триггеры и аудит.
- **Системное (UI):** ручной сквозной чек-лист ниже, поскольку Tkinter требует графической среды.

## 3. Виды и данные
Функциональное тестирование включает позитивные/негативные сценарии. Регрессия — повторный запуск всего набора после изменения кода. Данные: демо-роли `admin`/`user`, уникальная тестовая техника, валидное будущее время, время в прошлом, некорректная дата, конфликтный слот, дубликаты и чужая техника. Данные создаются заново в тестовой БД.

## 4. Запуск
Из корня проекта: `python -m unittest discover -s tests -v`. Отчёт покрытия: `coverage run --source=business_logic,data_access -m unittest discover -s tests` и затем `coverage report -m`. Coverage — необязательная dev-зависимость; приложение работает только на стандартной библиотеке.

## 5. Трассировка требований
| ID требования | Требование | Тесты/проверка |
|---|---|---|
| AUTH-01 | Успешный/неуспешный вход | `test_login_success`, `test_login_wrong_password` |
| AUTH-02 | Регистрация, уникальность и валидация | `test_register_valid`, `test_register_duplicate`, `test_register_invalid_username` |
| TECH-01 | Тип и модель техники валидны | `test_add_tech_invalid_model`, `test_add_duplicate_tech` |
| BOOK-01 | Создание записи | `test_book_appointment` |
| BOOK-02 | Проверка формата/прошлого времени | `test_reject_bad_datetime`, `test_reject_past_datetime` |
| BOOK-03 | Нельзя занять тот же слот | `test_conflicting_specialist_time_rolls_back` |
| SEC-01 | Пользователь не управляет чужой техникой | `test_user_cannot_book_other_users_tech` |
| SEC-02 | Отчёты только администратору | `test_user_cannot_view_admin_report` |
| BOOK-04 | Отмена записи | `test_cancel_appointment` |
| DB-01 | FK, представления и аудит | `test_foreign_keys_enabled`, `test_required_views_exist`, `test_audit_created_for_tech_insert` |
| REP-01 | Админ-отчёт и просмотр аудита | `test_admin_report_and_audit` |

## 6. Ручной системный чек-лист UI
- [ ] Запустить `python main.py`, проверить создание БД при первом запуске.
- [ ] Войти как `user` / `user123`; добавить устройство каждого разрешённого типа.
- [ ] Создать запись на ремонт, чистку и диагностику с будущей датой.
- [ ] Проверить пустые поля, неверный формат даты, дату в прошлом и занятый слот: должно появиться понятное сообщение.
- [ ] Отменить запланированную запись и убедиться, что статус обновился.
- [ ] Убедиться, что пользователь не видит административные отчёты/аудит.
- [ ] Войти как `admin` / `admin123`; открыть отчёты и аудит.
- [ ] Перезапустить приложение и убедиться, что данные сохраняются.

## 7. Журнал дефектов
| ID | Описание | Шаги воспроизведения | Severity | Priority | Статус |
|---|---|---|---|---|---|
| BUG-001 | Дефекты, найденные после запуска набора, регистрируются здесь | Заполнить фактическими шагами | — | — | Нет открытых дефектов по автоматическому прогону |

## 8. Протокол тестирования
- Дата: заполнить при сдаче/повторном запуске.
- Команда: `python -m unittest discover -s tests -v`.
- Последний зафиксированный прогон: **18 тестов, OK, 0 ошибок, 0 провалов**.
- Системный UI-чек-лист не автоматизирован и должен быть отмечен исполнителем в графической среде.
- Регрессия: повторить команду после каждого исправления; обновить таблицу дефектов и дату прогона.

## 9. Отчёт покрытия
Численное покрытие зависит от версии Python и конкретного запуска. Получить воспроизводимый отчёт командой из раздела 4; не указывать неподтверждённый процент. Команда создаёт `.coverage` (служебный файл) и выводит покрытые/непокрытые строки для BLL и DAL. GUI и ручные сценарии этим отчётом не покрываются.
